# bffi-object

[![License: MIT](https://img.shields.io/badge/License-MIT-3DA639)](https://github.com/DotBlood/bffi-rs/blob/main/LICENSE)
[![Rust](https://img.shields.io/badge/Rust-1.98.0-DEA584?logo=rust&logoColor=white)](https://github.com/DotBlood/bffi-rs/blob/main/rust-toolchain.toml)

Object ownership crate of [bffi-rs](https://github.com/DotBlood/bffi-rs/blob/main/README.md) - the Bun-only native
binding framework. Rust values live as `Arc<T>` inside the process-wide
[`Registry`](https://github.com/DotBlood/bffi-rs/blob/main/crates/bffi-core) and JavaScript only ever
sees an opaque `u64` handle, per the ownership contract in
[docs/DESIGN.md](https://github.com/DotBlood/bffi-rs/blob/main/docs/DESIGN.md) §6.2.

**Status:** P1 core complete - [`ObjectWrap`] over generational handles with
three use-after-free barriers. The C ABI exports and the JS-side wrapper are
generated by `bffi-macros` / `bffi-build` (P2) on top of these primitives.

## Why ObjectWrap

Crossing the C ABI means JavaScript holds raw integers, so a native object
must never be handed over as a reference. [`ObjectWrap`] is the typed
ownership layer above the registry:

- **Rust owns the value.** Every wrapped object is stored as `Arc<T>` in the
  global [`Registry`](https://github.com/DotBlood/bffi-rs/blob/main/crates/bffi-core);
  JS receives only the opaque `u64` handle.
- **One tag = one type per process.** [`ObjectWrap::new`] claims the tag in
  the registry and fails with `ObjectError::TagInUse` on a second claim, so a
  handle of one type can never be reinterpreted as another. Tags live in the
  reserved range `0x0100-0x01FF`.
- **Initialize once.** The wrap is just `(tag, marker)` - `Copy`,
  `Send + Sync` - so claim the tag once in a `OnceLock` static and share it:

```rust
static WRAP: OnceLock<ObjectWrap<Session>> = OnceLock::new();
```

## Use-after-free barriers

Every `get` / `release` passes three barriers (kanboard 4.2); any failure
yields `ObjectError::InvalidHandle`:

| # | Barrier        | Rejected input                                            |
| - | -------------- | --------------------------------------------------------- |
| 1 | Null           | `Handle::NULL` never resolves to an object                |
| 2 | Type tag       | a handle whose tag does not name this wrap's table (type spoofing) |
| 3 | Generation     | a stale handle stays dead after release, even if the slot is reused |

All three report the same error. Display text (exact, for a handle
`Handle(tag:0x0101, gen:3, idx:7)`):

```text
object handle Handle(tag:0x0101, gen:3, idx:7) is stale (already released) or belongs to another type
```

`From<ObjectError> for BffiError` maps it onto the existing
`ErrorCode::InvalidHandle`, preserving the domain error as the source.

## Arc-lenient release

`release(handle)` frees the SLOT in the registry and returns the last table
`Arc<T>`. Existing `Arc` holders keep the value alive - the memory goes away
only with the last reference, while the handle itself goes stale
immediately (P1-SPEC §5, arc-lenient ownership).

## JS contract (P2, documented only)

Not implemented yet - recorded here so the storage choice is explainable.
The P2 JS wrapper holds the `bigint` handle and ties the lifetime to the
JS object:

```text
FinalizationRegistry -> release export -> Registry::global().remove(handle)
```

The release export is type-erased (it only needs the `u64` handle). This is
WHY the storage lives in the process-wide `Registry`: a finalizer running
later, from any context, can free the slot without knowing `T`.

## Quick start

```rust
use std::sync::OnceLock;

use bffi_core::TypeTag;
use bffi_object::ObjectWrap;

struct Counter {
    n: u32,
}

// One tag per type per process; claim it once in a static.
static COUNTERS: OnceLock<ObjectWrap<Counter>> = OnceLock::new();
const COUNTER: TypeTag = TypeTag(0x0142);

let wrap = COUNTERS.get_or_init(|| ObjectWrap::new(COUNTER).expect("tag 0x0142 free"));
let handle = wrap.wrap(Counter { n: 7 }).expect("room");
assert_eq!(wrap.get(handle).expect("live").n, 7);
let released = wrap.release(handle).expect("live handle");
assert_eq!(released.n, 7);          // the Arc outlives the slot
assert!(wrap.get(handle).is_err()); // the handle is stale now
```

## What does _not_ belong here

Per DESIGN §8-9 (one responsibility per crate):

| Concern                                    | Home                        |
| ------------------------------------------ | --------------------------- |
| Numbers / strings / buffers conversion     | `bffi-types`                |
| Callback registration and marshalling      | `bffi-callback`             |
| `#[bffi]` and C ABI generation             | `bffi-macros`, `bffi-build` |
