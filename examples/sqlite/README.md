# examples/sqlite - the full-pipeline reference example

A small functional SQLite surface (open / exec / query / close) that
runs a REAL workload (open a database, run SQL, fetch rows) across the
bffi boundary. The point is not sqlite itself: this crate is the
canonical end-to-end verification of the `@z2net/bffi` pipeline -
ONE call from JS builds, generates, resolves, loads and drives a
native module.

## File map

```
examples/sqlite/
├── Cargo.toml            # cdylib + rlib; deps = the bffi stack + rusqlite
├── package.json          # private marker; the example is a Bun test target
├── .bffi/
│   ├── bffi.json         # THE config: crate name/binary, target dir, features
│   ├── bffi.api.json     # loader JSON emitted by `emit-json` (schema v1)
│   └── api.gen.ts        # GENERATED typed module (regenerated by the pipeline)
├── src/
│   ├── lib.rs            # the Rust surface + the runtime ABI expansion
│   ├── module_def.rs     # THE single descriptor aggregation (ModuleDef)
│   └── bin/emit_json.rs  # materializes .bffi/bffi.api.json from module_def
└── test/sqlite.test.ts   # the e2e suite (bun test doubles as the test)
```

## The pipeline this example verifies

```ts
const api: Api = await bffi({ config: `${import.meta.dir}/../.bffi/bffi.json` });
```

`bffi()` (from `@z2net/bffi`) performs, in order:

1. **cargo build** - `cargo build --release -p bffi-example-sqlite`
   (the workspace relocates `target/` to the repo root via
   `crate.targetDir`, so every example shares one build cache);
2. **loader JSON** - reads `.bffi/bffi.api.json` and validates it
   against schema v1 (this file is COMMITTED; it is emitted by the
   `emit-json` binary from the single `module_def::MODULE`
   aggregation - one source, one artifact);
3. **generation** - renders `.bffi/api.gen.ts`, a typed module whose
   schema literal drives `ApiOf<>`; exact TypeScript signatures with
   zero hand-written types (the write is skipped when byte-identical);
4. **resolution** - computes
   `target/release/bffi_example_sqlite.dll|so|dylib` for the running
   platform;
5. **dlopen** - declares every export for `bun:ffi` from the schema
   (each non-unit return becomes a trailing out-parameter slot) and
   returns the typed `Api`.

## The Rust surface and what each function proves

| Export | Signature (Rust) | Boundary path exercised |
| --- | --- | --- |
| `sqlite_version` | `() -> String` | static string return: copied into a transient buffer, JS reads it through the `bffi_buffer` pair and frees it |
| `open` | `(path: &str) -> Result<u64, SqliteError>` | cstring parameter (bun:ffi hands over NUL-terminated UTF-8); a `u64` handle return through the out-slot |
| `exec` | `(handle: u64, sql: &str) -> Result<(), SqliteError>` | handle routing + the unit return |
| `query` | `(handle: u64, sql: &str) -> Result<String, SqliteError>` | rows are assembled into one JSON string IN RUST and returned through the buffer pair |
| `close` | `(handle: u64) -> Result<(), SqliteError>` | explicit release of the wrapped object |

## How one call travels (open)

```
JS api.open(":memory:")
  -> generated shim bffi_open(path_ptr, __ret: *mut u64) -> u32
     -> Connection::open(path)                    (rusqlite)
     -> ObjectWrap<SharedConnection>.wrap(..)     (tag 0x0110, global Registry)
     -> __ret <- generational handle (u64)
  -> status 0; JS receives the handle as a bigint
```

Why a `Mutex<Connection>` inside the wrap: rusqlite's `Connection`
is `Send` but not `Sync`; the ObjectWrap stores `SharedConnection`
(Copy + Send + Sync), so any thread the pipeline touches it from
locks the inner mutex.

Why a generational handle: the handle carries `tag | gen | idx`; when
`close` releases the slot the generation advances, so a stale JS-side
bigint can never reach a reused slot. The e2e suite pins this -
`exec` on a closed handle throws with "bad handle".

## How errors cross

`Result<T, SqliteError>`: the generated shim stores the error as the
thread-local LAST ERROR (`bffi_error_*` runtime exports) and returns
`ErrorCode::DomainError (13)`. The JS `call` helper sees a non-zero
status, drains `takeError()` and throws an `Error` whose `cause`
carries the domain source ("division by 0"-style messages survive the
boundary losslessly). The test suite asserts both the throw and the
cause.

## The e2e suite (test/sqlite.test.ts)

- the pipeline builds, generates and loads (`await bffi(...)`);
- `sqlite_version` returns a non-empty engine version;
- open -> exec (CREATE/INSERT) -> query -> JSON.parse round-trips a
  real table with exact rows;
- invalid SQL surfaces as a thrown Error with the rusqlite cause;
- a closed handle is rejected (`InvalidHandle` + "bad handle").

The first test carries a 10-minute timeout: a COLD release build
(LTO, whole workspace) exceeds bun's 5-second default.

## Run

```sh
bun test examples/sqlite     # from the REPOSITORY ROOT
```

The root tsconfig `paths` map `@z2net/bffi` onto the local package
sources; in a standalone project `bun add @z2net/bffi` replaces the
mapping. Requirements: Bun >= 1.4.0, the pinned Rust toolchain
(1.98.0, see rust-toolchain.toml).
